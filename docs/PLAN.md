# AI Daily Feed — персональная лента чтения

Персональная лента: собирает свежие записи из блогов AI-мейджоров и блогов лидеров мнений (Билл Гейтс и аналогичные), пишет к каждой короткое саммари и подробный пересказ, показывает на минималистичной странице GitHub Pages. Обновляется несколько раз в день без участия человека.

## Цель и критерии готовности

Готово, когда:

- По каждому источнику новые записи появляются в ленте в течение одного цикла обновления после публикации.
- Каждая запись имеет короткое саммари (2–3 предложения) и раскрывающийся подробный пересказ.
- Лента открывается на GitHub Pages, работает на телефоне и десктопе, грузится без внешних зависимостей.
- Обновление идёт по расписанию; сбой пайплайна не выглядит как «тихий день» (есть сигнал о сбое).

## Архитектура

Три части: пайплайн сбора → генерация саммари → статический фронт. Всё в одном репозитории, один push в `main` обновляет сайт.

```
GitHub Actions (cron 4×/день)
  └─ fetch.py      feedparser + scrape fallback → data/raw/<день>.json + state.json (seed first)
  └─ summarize.py  LLM (DeepSeek) батчами → data/items.json (короткое + digest), healthcheck
  └─ commit + push в main → GitHub Pages (Deploy from branch, root)
```

### Данные

- `sources.yaml` — список источников: имя, домен, feed-URL или scrape-селектор, категория.
- `state.json` — `last_seen` по каждому источнику (composite-ключ `source/url`). Коммитится **после** успешной классификации, не раньше: упавший LLM не должен съедать непрочитанные записи (self-healing refetch).
- `data/items.json` — канонический файл ленты. Схема записи:

```json
{
  "id": "<source>/<url-hash>",
  "source": "OpenAI",
  "category": "ai-major",
  "title": "…",
  "url": "https://…",
  "published": "2026-11-18T09:00:00Z",
  "summary": "Короткое саммари (2–3 предложения).",
  "digest": "Подробный пересказ: что нового, почему важно, детали."
}
```

### Формат саммари

- **Короткое** — 2–3 предложения на русском: что случилось, почему это значимо.
- **Подробный пересказ** — 5–10 предложений, структурированно: суть → ключевые детали/цифры → значение.
- Заголовок — оригинальный (англ); перевод по желанию — см. Open questions.
- LLM-вызовы только для **новых** записей, батчами по 6, temperature 0, strict JSON, 1 retry с текстом ошибки. Каждая запись обязана вернуться в ответе (ids echo + проверка покрытия).

### Фронт (минимализм, один файл)

`index.html` — один файл, inline CSS/JS, без фреймворков и сборки. Системный шрифт, тёмная/светлая тема через CSS-переменные.

- Лента: карточки по дате (новые сверху). В карточке — источник, дата, заголовок, короткое саммари.
- Клик по карточке раскрывает подробный пересказ + ссылку «Читать оригинал» (новое окно).
- Фильтр по категориям (AI-мейджоры / Лидеры мнений) и поиск по набору.
- Отметка «прочитано» в `localStorage` (незаметно, чисто для личного удобства).

## Обновление и деплой

- **Каденция**: cron каждые 6 часов (4×/день), плюс ручной `workflow_dispatch` (принудительный прогон). Public-репо Actions бесплатны; ~2 мин на прогон — далеко от лимитов.
- **Деплой**: GitHub Pages → «Deploy from a branch» → `main`, корень. Никакой отдельной gh-pages-ветки: сайт и данные в одном push.
- **Секреты**: `DEEPSEEK_API_KEY` в репозитории (Settings → Secrets and variables → Actions). Push внутри Actions — штатный `GITHUB_TOKEN` с `permissions: contents: write`.
- **Сигнал о сбое**: шаг `if: failure()` пишет короткий файл и (опционально) алертит. Тихий сбой (скрипт вышел 0, но ничего не сделал) ловится healthcheck-ассертами в `summarize.py`, а не статусом exit.

## Этапы (каждый завершается проверкой, «go» — явно)

1. **Репозиторий и скелет.** Владелец создаёт public-репо (создание репо — только владелец, в web UI). Кладём пустые `index.html`, `data/items.json`, `sources.yaml`. Включаем Pages. *Проверка: live-страница открывается.*
2. **Верификация источников.** Живой `curl` по каждому feed-URL (локально `--ssl-no-revoke`). Для тех, где RSS нет, подбираем scrape-селектор. Фиксируем рабочий `sources.yaml`. *Проверка: каждый источник отдаёт ≥1 запись.*
3. **fetch.py.** Seed-режим (первый прогон: последние ~2 недели, лимит на источник) и инкрементальный режим. Записывает `data/raw/`, двигает `state.json` только после classify. *Проверка: seed прогон, N/N источников, 0 ошибок.*
4. **summarize.py.** Батч-саммари новых записей → `items.json` (merge + сортировка по дате), healthcheck (файл валиден, покрывает все входные записи). *Проверка: локальный прогон на сырых данных, валидный JSON.*
5. **Фронт.** Лента + раскрытие + фильтр + прочитано. *Проверка: в браузере, на узком экране.*
6. **Workflow.** Cron + dispatch, fetch → summarize → commit → push → failure-alert. *Проверка: dispatch, лента в live обновилась.*
7. **Прогон бэкфилла + верификация.** Seed на живом репозитории, затем Raw и live Pages с cache-busting (`?cb=$RANDOM`). *Проверка: счётчики сходятся, свежие записи на месте.*
8. **Финал.** HANDOFF.md, запись в INDEX.

## Риски и решения

- **Нет RSS у многих AI-блогов** → scrape fallback; селекторы хрупки → держать их в `sources.yaml` отдельно и алертить на пустой результат по источнику.
- **WAF/Cloudflare на отдельных блогах** → если источник стабильно не отдаётся, честно фиксируем как gap в `sources.yaml`, не маскируем под «нет новостей».
- **LLM-саммари: стоимость и надёжность** → только новые записи, батчи, temperature 0, retry, healthcheck покрытия.
- **Дрейф фидов/селекторов** → пустой результат по источнику = сигнал, а не тихий день.
- **GitHub Pages кэш** → верификация всегда с cache-busting.

## Non-goals

- Не агрегатор «всего» — только названные источники, только блоги/новости, не соцсети.
- Не полнотекстовый переводчик и не архив статей.
- Не приложение с бэкендом — статика, всё в Git.
